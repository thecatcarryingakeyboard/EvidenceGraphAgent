# 面试展示脚本

这份脚本用于把项目讲清楚，而不是把所有文件逐个讲一遍。一次演示控制在五到十分钟。

## 1. 先说问题

“企业知识问答不是所有问题都走同一个 RAG。库存、价格、订单属于结构化事实；售后规则和跨文档总结属于非结构化知识。我的 Agent 先做护栏和规划，再在预定义 Cypher、Text2Cypher、GraphRAG 三类工具之间选择，最后只根据工具返回的证据生成答案。”

## 2. 展示一条离线链路

```bash
PYTHONPATH=src python -m enterprise_graphrag.cli agent "总结上线前检查项并说明没有证据时怎么办"
```

重点看输出中的：

- `steps`：`guardrails → planner → tool_selection → document_search → summarize → final_answer`；
- `selected_tools`：每个子任务实际选择的工具；
- `citations`：答案引用了哪一个 chunk；
- 没有命中时的拒答，而不是猜测。

## 3. 解释为什么需要三类工具

- **预定义 Cypher**：高频、稳定、容易审计的查询；
- **Text2Cypher**：面对新问题时根据 schema 生成只读查询，执行前做 schema 检查和 `EXPLAIN`；
- **GraphRAG**：处理文档语义、社区摘要、全局总结和多跳证据。

如果面试官问“为什么不全部交给向量库”，可以回答：结构化事实需要可验证的过滤、聚合和关系方向；如果全部交给生成模型，无法稳定保证数值和权限边界。

## 4. 解释可靠性边界

当前公开示例把可靠性拆成四个位置：

1. Guardrails 拒绝明显越界问题；
2. Tool 层只返回结构化结果和证据；
3. Neo4j 查询禁止写操作，并使用参数化查询；
4. 最终答案保留引用，证据为空时 abstain。

真实部署还需要接入认证上下文、文档 ACL、持久化 checkpoint、人工审批和线上评测；这些在路线图中列为后续工作，不把演示代码包装成生产平台。

## 5. 常见追问与回答方向

| 追问 | 回答方向 |
| --- | --- |
| GraphRAG 和 Neo4j 是什么关系？ | Neo4j 负责结构化实体关系查询；GraphRAG 负责由索引阶段生成的实体、关系、社区报告和文本单元上的检索。两者在 Agent 层统一成工具结果。 |
| Text2Cypher 会不会执行危险语句？ | 只接受只读语句，先做关键词和 schema 校验，再用 `EXPLAIN`，参数单独传入；生产环境还应使用数据库只读账号和查询超时。 |
| 为什么要 Planner？ | 复合问题需要拆成多个可独立执行的子任务，便于并行、重试和记录每个工具的证据来源。 |
| 没查到结果怎么办？ | 明确返回证据不足；真实系统可以在预算内改写问题、切换检索通道或请求用户补充，而不是直接编造答案。 |
| 如何评测？ | 离线先测命中、引用率、拒答率和工具路由；接入真实数据后增加检索召回、答案忠实度、延迟、成本和权限回归。 |

## 6. 诚实说明项目状态

这是一个学习型、可运行的参考工程。离线实现为了让面试官可以 `git clone` 后马上运行；LangGraph、Neo4j、GraphRAG 和模型服务是可选适配层。展示时主动说明这一点，反而比宣称“生产级”更容易让面试官继续追问设计细节。
